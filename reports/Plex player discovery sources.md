# Plex's Rebuilt Apps Stopped Publishing Players

An empty player list from `plex.tv/api/v2/resources` is the expected result in late 2026, not a fault in the request: that endpoint lists only devices that choose to publish their own connection details to plex.tv, and the Plex apps most people now run no longer do so. Plex removed the Companion "player" role from Plex Web and Plex for Desktop in 2022, shipped the redesigned mobile app without it in spring 2025, and users report the same loss on the new Android TV and Apple TV apps during 2026; Plex has announced none of these removals. The clients that still publish and accept commands are **Plex HTPC, Plexamp (music only), and TV apps still on the classic build with "Advertise as Player" switched on**. For a browser page that may talk only to plex.tv and the user's own server, the best list is the **server's `GET /clients`, filtered to entries whose `protocolCapabilities` include `playback`**, with plex.tv `player` resources kept as a second, lower-confidence source and `/status/sessions` used only to label and to confirm that playback started. The command route, `/player/playback/playMedia` on the server with `X-Plex-Target-Client-Identifier`, is the only one that keeps the page away from the player, but the evidence says the server forwards only to players it already lists in `/clients`. The empty-list message should therefore say that this is a limit of the Plex apps on the user's devices and name the apps that do work. Almost every point about server behaviour rests on library source code and forum reports, not Plex documentation, so nine facts listed at the end need a test against a real server before the design is fixed.

## A resources list with only servers is the normal state

`/api/v2/resources` is not the account's device list. Plex's own developer documentation describes the response only as "available PMS instances" and never mentions `provides`, Plex Companion, `/clients` or any `/player/` path ([developer.plex.tv](https://developer.plex.tv/pms/)). python-plexapi reads two separate endpoints: `https://plex.tv/api/v2/resources?includeHttps=1&includeRelay=1&includeIPv6=1` for resources, and `https://plex.tv/devices.xml` for every device that has signed in ([python-plexapi myplex.py](https://raw.githubusercontent.com/pkkid/python-plexapi/master/plexapi/myplex.py)). A device that is merely signed in appears in the second list and on the Authorized Devices page, and not in the first. **A player entry in resources is an undocumented side effect of an app registering its own LAN address with plex.tv**, which in practice has meant "remote control is on and working". When an iPhone on the classic app did publish, its entry carried a plain-HTTP local address on port 32500 ([python-plexapi issue #1447](https://github.com/pkkid/python-plexapi/issues/1447)).

The entry is also short-lived. One user who watched the endpoint in February 2025 saw a phone's entry vanish a few minutes after the iOS app was force-closed, and return only when "Advertise as Player" was toggled; the same user's Apple TV stayed listed while idle ([Plex forum 819563](https://forums.plex.tv/t/plex-on-apple-tv-4k-2022-wont-announce-as-player-to-be-controlled-from-plex-on-other-devices/819563?page=7)). The reverse error exists too: Plex for Windows kept appearing as a cast target after its setting was removed, and control then failed with "unable to connect to player" ([Plex forum 905499](https://forums.plex.tv/t/advertise-as-player-long-gone-but-still-advertises-as-player-windows/905499)). No Plex source defines `presence` or says how long an entry lives; python-plexapi documents `presence` only as "True if the resource is online" ([python-plexapi myplex.py](https://raw.githubusercontent.com/pkkid/python-plexapi/master/plexapi/myplex.py)). A `player` entry is a hint, and Home Assistant treats it as one, accepting a resource only when `"player" in x.provides and x.presence and x.publicAddressMatches` and then testing the connection ([Home Assistant plex/server.py](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/plex/server.py)).

The request parameters are not the cause. `includeHttps`, `includeRelay` and `includeIPv6` switch which connections are listed for each resource: without `includeIPv6=1` no IPv6 addresses are shown, and `includeHttps=1` is what yields the `plex.direct` addresses ([Plex forum 932971](https://forums.plex.tv/t/ipv6-address-is-not-announced-to-clients/932971/2)). Both python-plexapi and Home Assistant call the endpoint with an ordinary account token and no special headers, filter on the client side, and do receive player resources ([Home Assistant plex/server.py](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/plex/server.py)). None of the forum reports of an empty list was explained by a request parameter. Two questions stay open because no source addresses them: whether a managed-user, shared-user or server `accessToken` sees a narrower list than the owner's account token, and whether plex.tv filters by the caller's `X-Plex-Client-Identifier` or `X-Plex-Product`.

The explained cases of an empty or server-only list fall into five groups. The app has no player role or has lost it ([Plex forum 919707](https://forums.plex.tv/t/remote-control-api-removed/919707)). The setting is on but the entry lapses when the app closes ([python-plexapi issue #1447](https://github.com/pkkid/python-plexapi/issues/1447)). The player sits on a different network segment: a Fire TV on Wi-Fi was found only after it moved to the server's wired network ([Plex forum 832390](https://forums.plex.tv/t/fire-tv-not-advertising-as-player-cannot-connect-from-remote-companion-app/832390?page=2)). Headless Plexamp has no Plex Pass ([Plex forum 868408](https://forums.plex.tv/t/plexamp-headless-player-not-found/868408)). Or the reader is looking at the wrong list, since the server's `/clients` and plex.tv resources are filled by different mechanisms and have been seen to disagree ([python-plexapi issue #1447](https://github.com/pkkid/python-plexapi/issues/1447)).

## App generation, not platform, decides who can be commanded

The pattern across four years is removal by rewrite. A Plex forum moderator confirmed in July 2022 that control of Plex Web and Plex for Desktop "was recently removed", and a Plex team-side poster gave the reason as "high maintenance cost" combined with "extremely low usage" ([Plex forum 801759](https://forums.plex.tv/t/plex-players-no-longer-supporting-remote-control/801759)). The redesigned mobile app became the only mobile experience in spring 2025, with Plex promising only "more casting functionality" over the coming months ([PCWorld](https://www.pcworld.com/article/2653520/plexs-new-experience-arrives-6-things-to-know-before-updating.html)). A developer reported on 23 May 2025 that the new iOS app has no "Advertise as Player" option and refuses player commands despite a valid token ([Plex forum 919707](https://forums.plex.tv/t/remote-control-api-removed/919707)). In September 2026 a user of the new Android TV app (2026.16 to 2026.18) found `/clients` empty on every device, port 32500 refusing connections, and no reply to GDM discovery in a packet capture; a second user reported the same on the new Apple TV app ([Plex forum 943129](https://forums.plex.tv/t/remote-control-companion-casting-completely-broken-on-android-tv-since-new-plex-experience-serve/943129)). **No Plex staff statement confirming removal from the TV apps was found**; the evidence is user reports and one third-party developer. Plex's two Companion support articles now carry the note that they do "not apply to Plex for Mobile apps 2025.10 or higher" ([Plex support](https://support.plex.tv/articles/201812803-plex-companion-remote-control-issues/)), but their bodies could not be read (HTTP 403), so Plex's own per-app table is missing from this report.

## The server's client list is the only browser-safe list of command targets

Three things separate the candidate sources: whether the source says a player takes commands, whether it says the player is on now, and whether a browser page can read it under the constraint.

| Source | Says "takes commands" | Says "on now" | Token | Fit for the page |
|---|---|---|---|---|
| Server `GET /clients` | Yes, `protocolCapabilities` | Implied by discovery | Server token | Yes. Coverage is the weakness |
| plex.tv `/api/v2/resources` | Only `provides` contains `player` | `presence` flag | Account token | Yes, already in use. A hint only |
| Server `GET /status/sessions` | No | Yes, `state`, `local`, `relayed` | Admin token per the community spec | Yes for the owner. Label and confirmation only |
| plex.tv `devices.xml` | Only `provides` | No, `lastSeenAt` only | Account token | Reachable, but returns a token per device. Avoid |
| Server `GET /devices` | No | No | Admin token per the community spec | No value |
| GDM | Yes | Yes | None | Impossible: UDP |
| Player's own `/resources` | Yes | Yes | Token | Forbidden by the constraint |

**`/clients` is the list both reference tools treat as "controllable now".** python-plexapi's `PlexServer.clients()` is built only from it, reads `machineIdentifier`, `host`, `port`, `product` and `protocolCapabilities` from each entry, and raises `NotFound` for any name not in it ([plexapi server.py](https://github.com/pushingkarmaorg/python-plexapi/blob/master/plexapi/server.py), [plexapi client.py](https://github.com/pushingkarmaorg/python-plexapi/blob/master/plexapi/client.py)). The fields match what a player sends in its GDM reply, and every forum fix for an empty `/clients` is a GDM fix, so the list is almost certainly filled by the server's own LAN discovery ([plexapi gdm.py](https://github.com/pushingkarmaorg/python-plexapi/blob/master/plexapi/gdm.py), [Plex forum 777636](https://forums.plex.tv/t/clients-endpoint-not-reporting-correctly/777636)); no primary source says so outright. That explains its limits: the Home Assistant maintainer notes "the Plex server must also be on the same subnet as the Plex clients" ([python-plexapi issue #1447](https://github.com/pkkid/python-plexapi/issues/1447)), and a host firewall that blocks GDM empties the list. Plex's official API documentation, published in September 2025, does not document `/clients` at all ([developer.plex.tv](https://developer.plex.tv/pms/)), and the community OpenAPI spec gives it a response schema that matches a plex.tv resource, not what the server returns ([plex-api-spec](https://github.com/LukeHagar/plex-api-spec/blob/main/plex-api-spec.yaml)).

Home Assistant merges four sources on every update: the server's `/clients`, its own GDM scan, plex.tv resources filtered by `player`, `presence` and `publicAddressMatches` (refreshed at most every 60 seconds), and sessions ([HA plex/server.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/plex/server.py)). It then connects straight to each player, and uses the server proxy only when the player's address contains `127.0.0.1` ([HA plex/media_player.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/plex/media_player.py)). Its `play_media` refuses with "Client is not currently accepting playback controls" unless the connected device reports `playback` in its capabilities. Neither tool can be copied whole, because both read capabilities from the player over a direct connection. What transfers is the filter logic and one design choice: Home Assistant gives users a "scan clients" button because a device must be switched on before it can be found ([HA docs](https://www.home-assistant.io/integrations/plex/)).

Sessions cannot stand in for the client list. The `Player` element has a name, product, `machineIdentifier`, `state`, `local` and `relayed`, and no capabilities or port ([developer.plex.tv](https://developer.plex.tv/pms/)). python-plexapi says in its source that "since protocolCapabilities is missing from /sessions we can't really control this player" ([plexapi client.py](https://github.com/pushingkarmaorg/python-plexapi/blob/master/plexapi/client.py)), and Home Assistant marks a session-only player as visible but without controls. `devices.xml` over-reports (old sign-ins, scripts) and hands the page a token for every device ([plexapi myplex.py](https://github.com/pushingkarmaorg/python-plexapi/blob/master/plexapi/myplex.py)), so a page that needs only names should not call it.

One caveat applies to the plex.tv filter. `publicAddressMatches` compares the player's public address with the caller's ([python-plexapi myplex.py](https://raw.githubusercontent.com/pkkid/python-plexapi/master/plexapi/myplex.py)). For Home Assistant the caller sits next to the server. For a web page the caller is the browser, so the flag answers "is this player near the browser", which is the wrong question when the user is away from home and commands go through the server. The page should not drop a player on that flag alone.

## The server forwards only to players it already lists

A proxied command uses the same wire format as a direct one. python-plexapi's `sendCommand` builds `GET /player/<controller>/<command>` with an incrementing `commandID` and the header `X-Plex-Target-Client-Identifier: <player machineIdentifier>`; proxying changes only which host receives the request ([plexapi client.py](https://github.com/pkkid/python-plexapi/blob/master/plexapi/client.py)). Its `playMedia` first creates a play queue on the server, then sends `providerIdentifier=com.plexapp.plugins.library`, the server's `machineIdentifier`, `protocol`, `address` and `port`, plus `key`, `offset`, `type`, `containerKey=/playQueues/<id>?window=100&own=1` and a transient `token` from the server. Those fields match Plex's own Remote Control wiki, where `offset` is in milliseconds and the token is one "the controller obtains from the server for the player to use" ([Plex Media Player wiki](https://github.com/plexinc/plex-media-player/wiki/Remote-control-API)). The community spec disagrees on three points (it lists `playMedia` as a POST, calls `offset` a byte offset, and says an omitted target header sends to the "default/active client"), and it is the outlier ([plex-api-spec](https://github.com/LukeHagar/plex-api-spec/blob/main/plex-api-spec.yaml)).

The request shape is not the weak point; the server's knowledge of the player is. The wiki says controllers "MUST send commands directly" to native players and describes the server proxy as a facility for non-native ones, so proxying to an ordinary Plex app is observed practice, not a documented contract. In February 2024 a user with a Shield that had the advertise setting on, but an empty `/clients`, sent `/player/playback/play` to the server and got **HTTP 404**; the same command sent to the player's own address worked ([Plex forum 870187](https://forums.plex.tv/t/impossible-to-control-plex-locally-via-player-playback-endpoints/870187)). Plex's troubleshooting article, seen only through a search snippet, says an app missing from the server's `/clients` "won't be available to use for Plex Companion control" ([Plex support](https://support.plex.tv/articles/201812803-plex-companion-remote-control-issues/)). The working rule is therefore: **if the target is not in `/clients`, the server has nothing to forward to, and the answer is 404.** That rule rests on two user reports and on how the libraries behave.

It leaves one case unsettled, and it matters for the decision. In issue #1447 an iPhone and an Apple TV were absent from `/clients`, present in plex.tv resources, and controllable by Home Assistant over a direct connection. No source says whether a server-proxied command reaches such a player. A forum moderator has said some apps "are not allowed to open a network port themselves" and "depend on the presence of a plex server within the local network, to act as a remote relay" ([Plex forum 862449](https://forums.plex.tv/t/what-is-the-current-situation-with-remote-controller-operation-of-android-app/862449)), and the `pubsub-player` value in `provides` hints at delivery over a plex.tv channel, but no public description of that mechanism exists.

Success is hard to read from the response. Plexamp and Plex for Android answer a successful command with the bare body `OK`, Plex for Samsung with unterminated XML, and python-plexapi carries a workaround for exactly those product names ([plexapi client.py](https://github.com/pkkid/python-plexapi/blob/master/plexapi/client.py)). Some players accept a command and do nothing. Watching `/status/sessions` for the target's `machineIdentifier` after sending is the one check that works across players.

For the browser, plex.tv is safe ground: a direct probe on 2026-11-23 found every tested plex.tv endpoint answering preflight with `access-control-allow-origin: *` and accepting `X-Plex-Token` and `X-Plex-Client-Identifier` ([plex.tv resources](https://plex.tv/api/v2/resources)). The server is less certain. A 2020 Tenable advisory states that Plex Media Server returns `Access-Control-Allow-Origin: *` by default ([Tenable TRA-2020-35](https://www.tenable.com/security/research/tra-2020-35)), but no current source says which request headers its preflight allows. The proxied command adds one custom header, `X-Plex-Target-Client-Identifier`, that the list calls do not need. The 2024 forum poster passed it as a query parameter instead, and that request reached the server.

## Decision: list from /clients, explain the gap, and test nine facts

**Build the list from the server's `GET /clients`, keeping entries whose `protocolCapabilities` contain `playback`.** It needs only the server token and a request to the user's own server, it is the list the server itself appears to forward to, and it is the pre-flight check that Plex's own troubleshooting advice names. Add plex.tv resources with `player` in `provides` and `presence` true as a second source, joined to the first by identifier (`clientIdentifier` equals `machineIdentifier`); show a resources-only player as a target that has not been confirmed, until the test below says whether the server can reach it. Join `/status/sessions` by `machineIdentifier` to show what a player is doing and to confirm that a sent item started; never list a session-only player as a target. Do not call `devices.xml`. Offer a manual refresh, since players appear only after their app is opened. Treat three outcomes of a send separately: target absent from the list (do not send), 404 from the server (the player is not controllable now, not a malformed request), and 200 with an odd or empty body (accepted; confirm through sessions).

When the list is empty, the app should say that the cause is on the Plex side and what the user can do. Suggested wording:

> **No Plex players can take a "play this" command right now.** Plex only lets some of its apps be controlled from another device. Those that can: Plex HTPC, Plexamp (music only), and older Plex apps on a TV or streaming box with "Advertise as Player" turned on in the app's settings. Those that cannot, whatever their settings: the current Plex app on phones and tablets, the new Plex app on Apple TV and Android TV, Plex in a browser, and Plex for Windows or Mac. A player must also be open and on the same network as your Plex server. Open the Plex app on the device, then press Refresh.

The wording is deliberately specific about app generations, because a user who owns five Plex devices will otherwise assume the web app is broken. It should not promise that toggling a setting fixes the problem, and it should be reviewed whenever Plex ships a casting replacement.

These facts decide the design and have no reliable public source, so each needs a run against a real server:

| # | Fact to test | Why it matters |
|---|---|---|
| 1 | With Plex HTPC or Plexamp open on the server's network, does `/clients` list it, with which `protocolCapabilities`, and does a `player` resource appear on plex.tv? | Proves the request and the filter are right; gives a known-good control |
| 2 | Does a proxied `playMedia` reach a player that is in plex.tv resources but not in `/clients`? | Decides whether resources-only players are shown as targets at all |
| 3 | What status and body does the server return for a target it does not know, and for a redesigned app? | 404 rests on two anecdotes; the app's error handling depends on it |
| 4 | Does the server's CORS preflight allow `X-Plex-Target-Client-Identifier`, and does the server accept it as a query parameter instead? | A blocked header stops the feature in every browser |
| 5 | Does the server answer Chrome's private-network preflight when the page is served from a public origin over the `plex.direct` address? | A reported Chrome-only failure mode |
| 6 | Do `/clients` and `/status/sessions` answer for a shared or managed user's token, and what does that token get from plex.tv resources? | The community spec marks sessions admin-only; the official page disagrees |
| 7 | How soon does a player appear in `/clients` after its app opens, and how long after it closes does it remain? | Sets the refresh interval and how stale an entry can be |
| 8 | Is `playMedia` accepted as GET with the python-plexapi parameter set, and does the play queue `containerKey` form work on HTPC and Plexamp? | The community spec says POST; the libraries send GET |
| 9 | After a successful send, does the target's `machineIdentifier` appear in `/status/sessions`, and how quickly? | The only cross-player confirmation; one stale 2020 report says sessions did not update |

Two reading tasks sit beside the tests: open Plex's "Supported Plex Companion Apps" article in a browser, since it is the one official per-app table and could not be fetched, and check the current app version on each device the feature is meant to serve, since the classic or redesigned build decides everything.

## Conclusion

The question "which source lists the players" turns out to be the smaller half of the problem. Every list is downstream of one fact: a Plex app is a target only if it runs a Companion listener, and Plex has been shipping rewrites without one since 2022 and has not said so. A web app that sends "play this item" through the server is therefore building on an interface that is unannounced, absent from Plex's 2025 API documentation, and shrinking with each platform the redesign reaches. The feature is sound today for a household with Plex HTPC, Plexamp or classic TV builds, and it will reach fewer devices in 2027 than it does now unless Plex's promised casting replacement turns out to be open.

That argues for two design habits beyond the choice of endpoint. Treat the player list as a live probe of what the server can reach, not as a catalogue of the user's devices, and make the empty state a first-class screen that names the app generations involved. And keep the send path cheap to replace: if Plex ships a new cross-device mechanism, the part of this design that survives is the session-based confirmation, not the `/player/` call.
