# Plex Poster Display — Product and Technical Spec

Baseline: commit `3a7b688` (v2.0.0, PWA rewrite). Run start: `46257c3` (the commit that recorded the owner's rulings). Target: v2.1.0. Companion plan: `docs/integration-plan.md`. Binding rulings: `docs/decisions.md` (D1-D16); every behaviour below that a ruling set cites its D-entry.

Revision r3 (planning re-dispatch): lean scope per D1, rulings D2-D16 applied, the r1 review findings closed, and the r2 confirmation findings (N1-N10) closed. Q19-Q23 were settled by the conductor at the r2 confirmation (see *Open questions*).

## Goal

A poster display that can run unattended, 24/7, on any screen in the house without damaging that screen, leaking the owner's Plex access, or needing a keyboard to set up.

## Personas and use cases

| Persona | Setup | What matters |
|---|---|---|
| **Hallway-OLED owner** | 55" OLED mounted in portrait, Raspberry Pi 4 behind it running Chromium `--kiosk`, on 24/7, kids in the house | No burn-in (static frame, status text), no SD-card wear, screen off when nobody is home, kids cannot reconfigure or reach the token, random posters stay age-appropriate, no keyboard on the device |
| **Wall-tablet owner** | Android/iPad tablet in a stand, installed PWA, touch only | Touch-friendly controls (no accidental taps), battery safety when always charging, swipe-back or pinch must not leave the app, config from the tablet itself |
| **Landscape-TV owner** | 1920x1080 TV driven by a Pi or Chromecast-class browser, rotation 0 or a screen mounted sideways | A portrait poster fills only about a third of the screen, so fill modes matter. Rotation must not clip. Remote-control (D-pad) navigation, no mouse |

Use cases: UC1 show what is playing now; UC2 rotate random posters when idle; UC3 survive Plex or network outages; UC4 first-time setup without a keyboard (R-FIRST-1, D3); UC5 leave it alone for months; UC6 hand the device to a household with children.

## Principles

1. **Zero runtime dependencies, no build step.** Plain ES modules, static files. Dev-only dependencies (the Playwright e2e harness) are allowed, must appear only under `devDependencies`, and need a committed `package-lock.json` (D15).
2. **Works offline and with no backend.** The app is fully functional as static files. Anything that needs a process (the device helper) is opt-in, loopback-only, and the app degrades silently when it is absent.
3. **Protect the hardware by default.** Imperceptible protections default on; protections the user would notice (blanking, dimming, content limits) default off but are one tap away (R-PROT-5; the content limit is its own toggle, D5).
4. **Secrets stay off the display surface.** The Plex token is never placed in a QR code, an export (unless ticked), a log line, a helper response or a receipt. It does appear in Plex request URLs (`X-Plex-Token` query parameter, and in `<img src>` when `directImages` is on) because the Plex API and `<img>` need it; this is by design and not changed here. Any command a human runs against plex.tv sends the token as a header, never in a URL.
5. **Match the existing idiom.** Pure logic in small modules with `node --test` tests; DOM glue in `main.js`, `display.js`, `settings-ui.js`.
6. **Facts we cannot verify here are marked (verify)** and collected in `docs/validation/` for the hardware/real-server phases.

## Supported topologies

**R-TOPO-1 (P1, sceptic M2) Which device setups are supported.** A page served over plain `http://<lan-ip>` is an insecure context: no service worker, no install prompt, no Cache API (so no offline posters), no Wake Lock, no `crypto.subtle` (the PIN uses a fallback hasher, R-KIOSK-1). The supported topologies are:
- **Kiosk Pi, local server:** Chromium on the Pi opens `http://localhost:8080` served by `scripts/serve.mjs` on the same Pi. `localhost` is a secure context, so everything works.
- **Installed tablet or TV browser:** the app must be hosted over https (any static host) so it is a secure context; Plex is then reached through its `*.plex.direct` https address after sign-in. `serve.mjs` features (config guard, helper) do not apply to this topology.
- **Tablet loading the Pi's http LAN address:** works as a plain web page only; the docs say what is lost and recommend one of the two topologies above.
- Acceptance: the README has a "Supported setups" section naming these three topologies and the missing capabilities for the third (checked by `docs`); Diagnostics shows `Secure context: yes|no` and `Service worker: controlling|none` (checked in `pi-stability`).

## Requirements

Priorities: **P0** fix-first, **P1** protection, **P2** polish, **P3** bigger features. Each requirement names the finding IDs it answers. Every requirement carries acceptance bullets written so a script can check them; the plan turns them into commands. Pixel shift (R-PROT-2) is on by default, so every e2e spec that measures stage geometry runs with `pixelShift:false` seeded by the harness unless it is testing pixel shift.

### Rotation and layout

**R-ROT-1 (P0, F1) Rotated stage stays centred and on screen.** `.stage` is a flex/grid child of `.app` (`css/app.css`); at rotation 90/270 on a landscape viewport the stage is laid out at swapped dimensions (`stageSize()` in `js/layout.js`), so its layout box (e.g. 1080x1687 in a 1920x1080 viewport) is taller than the container, grows the grid row, and the rotated result lands about 300 px low and clipped. Fix: take the stage out of flow and centre it on the viewport centre (absolute at 50%/50% with `translate(-50%, -50%)` composed in `transform` before `rotate`; the individual `translate` property stays free for pixel shift).
- At 1920x1080, 1080x1920 and 1280x800, for each rotation 0/90/180/270 with `pixelShift:false`: `#stage` and `#frame` bounding boxes lie inside the viewport (tolerance 1 px) and their centre is within 1 px of the viewport centre.
- The stage's rotated bounding box is the largest that fits the viewport for that rotation: its limiting dimension equals the viewport dimension within 2 px.
- `.app` has no scroll overflow (`scrollHeight == clientHeight`).
- Existing `tests/layout.test.js` still passes unchanged.

**R-ROT-2 (P0, F2; D2) The UI shell rotates with the stage.** Controls, toast, status indicator, empty-state card, Settings sheet, Diagnostics and every new dialog read upright for the viewer at rotation 90/180/270. Setting `rotateUi` (default true) turns this off for users who rotate the OS instead (documented as an option; OS rotation with `rotateUi` off and app rotation 0 stays supported).
- With rotation 90, 180 and 270 and `rotateUi` true, the computed transform angle of each of `#controls`, `#toast`, `.empty-card`, `#settings`, `#diagnostics` and `#status-dot` (checked in `status-indicator`, where the dot is created) equals the stage rotation, and each element's bounding box (opened/visible) lies inside the viewport.
- The controls bar sits at the viewer's bottom-right at every rotation.
- With `rotateUi` false, none of those elements carries a rotation.
- Rotation 0 layout is unchanged (bounding boxes equal the `rotateUi:false` values).
- A top-layer `<dialog>` ignores ancestor transforms, so each dialog gets its own rotation rule driven by `--ui-rotation`, `--vw`, `--vh` set by `display.layout()`. The backdrop stays full-screen.

### Status indicator

**R-STAT-1 (P0, F5) No persistent status text.** `#status` (re-rendered every second with a countdown) becomes: visible only while the controls are visible; otherwise, when there is something to report (paused, offline), a small low-contrast dot (`#status-dot`, at most 8 px, at most 40% opacity) that changes corner position on a slow cycle (every 5 minutes, by whole steps). When all is well and controls are hidden nothing is drawn. "Can't reach Plex" and "Offline" mean the server did not answer: a token rejected or a selection that matches nothing is an answer, which the empty card explains, so neither shows the connection message or the dot (D132). The 1 s `setInterval(updateStatus)` in `js/main.js` runs only while the pill is visible. Setting `statusIndicator` (`dot` default, `off`). On by default (D6).
- With the mock server stopped and controls idle-hidden, `#status` is hidden, `#status-dot` is visible and no larger than 8x8 px with opacity at most 0.4; after waking the controls `#status` shows the retry countdown.
- With everything healthy and controls hidden, neither element is visible, and a `MutationObserver` on `#status` records 0 mutations over 3 s.
- The dot's corner differs after the cycle interval (fake clock) and is always inside the viewport; `statusIndicator:'off'` hides it.

### Poster cache and SD-card wear

**R-CACHE-1 (P0, F3, E8) Cache-first poster fetch.** `fetchImage()` in `js/main.js` must consult `poster-cache.js` before the network. A cache entry is valid when its stored `thumb` equals the requested poster's `thumb` (Plex changes the thumb path when artwork changes) and its stored pixel size is at least the requested size. On a hit nothing is downloaded and nothing is written to the Cache API. On a miss the existing download-and-put path runs. Corner cases: `directImages` mode (CORS blocked) is unchanged; a cache read error falls back to the network. On by default (D6).
- Showing 8 distinct posters 3 times each causes at most 8 `/photo/:/transcode` requests (counted by the mock's stats endpoint) and at most 8 Cache API writes.
- Unit tests cover: hit, miss, thumb changed, stored smaller than requested, stored larger, storage error.
- A poster whose artwork changed is re-downloaded exactly once.

**R-CACHE-2 (P0, F3) Cache sized to the pool.** New setting `posterCacheLimit` (default 100, range 10-300). `createPosterCache` reads the limit lazily so a settings change applies without reload. With the default random pool of 100 titles, steady state is zero downloads and zero writes per rotation (previously 288 of each per day at 5-minute rotation). Index metadata stores the pixel size.
- A unit test shows the limit read as a function on every `put` and eviction removing the evicted Cache API entries.
- After the 8 posters are cached and the page reloaded, showing the same 8 again produces 0 transcode requests.

### Security

**R-SEC-1 (P0, F4; D9) The local server serves only the app, and `config.json` only to loopback.** `scripts/serve.mjs` serves an **allowlist** of paths: `/` and `index.html`, `manifest.webmanifest`, `sw.js`, and anything under `css/`, `js/` and `assets/`. `config.json` is served only to a request whose socket peer address is loopback (`127.0.0.0/8`, `::1`, `::ffff:127.x`) **and** whose `Host` hostname is `localhost`, `127.0.0.1` or `[::1]`. Everything else (`.orchestrator/`, `docs/`, `README.md`, `package.json`, `tests/`, `scripts/`, dotfiles) is 404 for every client. The path is normalised (decoded, `.`/`..` resolved, trailing slash stripped, case-folded for the `config.json` test) before either rule is applied. The Host check compares the **hostname only** and ignores the port (browsers send `localhost:8080`); parse it with `new URL('http://' + host).hostname`. `X-Forwarded-For` and `Forwarded` are never consulted. Exports `isLoopback(addr)` and `isLoopbackHost(hostHeader)` from `scripts/net.mjs`, reused by R-HELP-1.
- Started with `--host 0.0.0.0`: `GET /config.json` from loopback with `Host: localhost:<port>` returns 200; from the machine's LAN address returns 403; a request from the LAN address that sends `X-Forwarded-For: 127.0.0.1` still returns 403; `GET /index.html` from the LAN address returns 200.
- From the LAN address, `/.orchestrator/x.md`, `/docs/spec.md`, `/package.json` and `/README.md` return 404, as do `//config.json`, `/./config.json`, `/%63onfig.json`, `/config.json/` and `/CONFIG.JSON` (none returns 200).
- A loopback peer sending `Host: evil.example` or `Host: localhost.evil.com` is refused for `config.json`; `Host: localhost:8080` and `Host: [::1]:8080` are accepted.
- Unit tests for `isLoopback` cover IPv4, IPv6, IPv4-mapped IPv6, empty and undefined; for `isLoopbackHost` cover with and without port. The integration test spawns the server on a free port, never a fixed one, so concurrent worktrees do not collide (D12).

**R-SEC-2 (P0, S1; D14) Token rotation.** The first commit (`5c4a716`) contains `config.js` with a real Plex token; it remains in git history. The owner must rotate the token (a human act, `mode: hitl`) and record a receipt. The hand-off lists both rotation routes **(verify which one revokes the leaked token)**: (a) plex.tv > Account > Authorized Devices, remove the device or sign out everywhere; (b) change the account password and tick "Sign out of connected devices". The owner's rejection check sends the token as an `X-Plex-Token` request header read from a file descriptor, never in a URL or on the command line. Purging history (`git filter-repo` plus force-push) is optional, irreversible, **skipped unless the owner says the repository is public or shared**, and outside the release path.
- `docs/security/token-rotation.md` records `Rotated: yes`, the date, the method and "old token rejected (HTTP 401)".
- The receipt contains no token-like string (no `X-Plex-Token` text and no alphanumeric run of 20 or more characters).
- If the owner opts in to a purge, a fresh clone of `origin` has no commit that touches `config.js`.

An automatic reload (daily, after wake, update) waits until position mode ends, so an unsaved placement is not dropped.

### Controls and input

**R-CTRL-1 (P2, U11) Control labels.** Each control button gets a visible label: a CSS tooltip on hover/focus, and on touch devices (`(hover: none)`) a text label under the icon. Setting `controlLabels` (`auto` default: labels on touch only; `always`; `never`).
- With `(hover: none)` emulated, each of the 7 control buttons shows a text label; on desktop only a tooltip on hover/focus and no persistent label; `always`/`never` override.

**R-CTRL-2 (P2, U12; sceptic I10) First tap only wakes the controls.** The first tap swallows the click **only when all hold**: the controls were hidden when the pointer went down, the target is inside `#controls` (or is the bare stage), no dialog is open, and `pointerType !== 'mouse'`. The `click` generated after the revealing `pointerdown` is swallowed; a second tap activates. Mouse and keyboard behaviour is unchanged. A tap inside an open Settings or Diagnostics dialog, or on a button in the empty-state card, is never swallowed.
- Touch, controls hidden: a tap on the Settings button's position reveals the controls and does not open Settings; the second tap opens it; the same for Pin and Rotate (rotation unchanged after the first tap).
- Touch, Settings open for longer than the controls' hide delay: a tap on Save is not swallowed. Touch, empty-state card: a tap on "Open settings" is not swallowed.
- A mouse click on a visible button works on the first click.

**R-CTRL-3 (P2, U13) Shortcut overlay.** Pressing `?` (or a "Keyboard shortcuts" button in Diagnostics) opens a dialog listing every shortcut, generated from the same table that drives `KEYS` in `js/main.js` so the two cannot drift. Esc closes. With `disableShortcuts` the overlay is not listed or opened.
- The table has `r p space o f s d ?` with a label each and no duplicate keys; `listShortcuts({disableShortcuts:true})` is empty.
- `?` opens the dialog with at least 8 entries generated from the table (at rotation 90 `#shortcuts`' computed angle is 90 and its box lies inside the viewport); Esc closes it; with `disableShortcuts:true`, `?` does nothing.

**R-CTRL-4 (P2, D96) The controls hide on their own.** Pointer, key or mouse-wheel activity shows the controls, and they hide 3.5 s after the last activity. Only two things hold them past that. A mouse or pen resting over them holds them, but not after a touch: a finger leaves the tapped button in `:hover`. Focus inside them holds them only for a keyboard user: a Tab outside any open dialog starts keyboard use, and a pointer press, a mouse that actually moves or a mouse wheel ends it. That hold ends 30 s after the last key press (any key); the focus stays where it is, and the next key press shows the controls again. A Tab between the fields of an open dialog is not keyboard use. So when Settings, Diagnostics or the shortcut overlay closes, focus returns to the control that opened it but does not hold the controls, whatever closed the dialog (Save, Cancel, Esc) and whether a mouse, a touch or the `s` shortcut opened it. Kiosk mode never shows them on activity. Focus is never moved.
- Mouse: open Settings, close it by Save, Cancel or Esc, keep still → the controls hide within 3.5 s; a mouse move shows them again and they hide again. The same after Diagnostics and after `?`.
- Mouse: click into a Settings field, Tab, Esc, mouse still → the controls hide. Touch: a tap on Pause, Pin poster, Refresh or Rotate → the controls hide afterwards.
- Keyboard: Tab into the controls → they stay shown while focus is on them and keys are pressed; 30 s after the last key press they hide (focus stays on the control) and the next key press shows them again. A real mouse move away, or a mouse wheel, ends keyboard use: they hide 3.5 s later, with focus still on the control.

**R-CTRL-5 (P2, D100) D-pad navigation of the controls.** The arrow keys of a TV remote move focus between the control buttons. With no dialog open, position mode off and the controls not inert, ArrowLeft, ArrowRight, ArrowUp and ArrowDown move focus to the nearest visible, enabled button in that direction as it appears on screen (bounding-box centres, so `rotateUi` and rotation are followed); with no button that way, focus stays (no wrap). The page does not scroll: `preventDefault` is called only when the arrow is consumed. When the controls are hidden, the first arrow only shows them and puts focus on a control (the last focused one if it is still there, else the first) and activates nothing; later arrows move. OK or Enter on a focused button activates it, as in any browser. An arrow counts as keyboard use, like Tab, so the 30 s hold of R-CTRL-4 applies; an arrow inside an open dialog does not, and keeps its native behaviour (selects, sliders, text fields, the PIN keypad). Position mode keeps its arrows. `disableShortcuts` does not turn this off: the arrows are navigation, not shortcuts. In kiosk mode an arrow never shows the controls; during the 15 s reveal, while the controls are not inert, arrows navigate them.
- Hidden controls: ArrowRight shows them and focuses a control; nothing is activated and no dialog opens. Then ArrowRight and ArrowLeft move to the next and previous button, Enter on Settings opens Settings, and no key past the last button wraps.
- In Settings an arrow changes a select or slider natively and focus does not jump to the controls. At rotation 90 with `rotateUi` the arrows follow the screen. An arrow holds the controls for 30 s after the last key, then they hide. Kiosk: an arrow does not show them. Position mode: arrows still move the poster. `disableShortcuts: true` leaves the arrows working.

### Frame brightness

**R-FRM-4 (P1, E4) Frame brightness and night dim.** Setting `frameBrightness` (10-100, default 100) applies `filter: brightness()` to the frame image. Night dim: `nightDim` (default **false**, D6), `nightDimStart` 22:00, `nightDimEnd` 07:00, `nightDimLevel` 60, and `nightDimTarget` (`frame` default | `stage`; `stage` also dims the poster, D6 "whole-poster dim option"). The level is recomputed **once a minute in whole steps** (no CSS transition and no animated filter, resolving the conflict with R-PROT-4): dimming ramps in over the first 10 minutes after `nightDimStart` and out over the last 10 minutes before `nightDimEnd`, so the change is never a jump. The filter is placed on `#frame` (target `frame`) or `#stage` (target `stage`) only. Schedules wait for a plausible clock (R-PROT-6). With the device helper there is no hardware brightness (dropped, D8).
- Pure `effectiveBrightness(now, settings)` is unit tested: manual level, night window incl. midnight crossing, the 10-minute ramps at both boundaries, `min` of manual and night level, `nightDim:false`, and a DST night.
- At 12:00 with `nightDim` on, `#frame` computes `filter: none`; at 23:00 `brightness(0.6)` (±0.02); `frameBrightness:50` gives `brightness(0.5)`; the poster layers have `filter: none` when the target is `frame`.
- With target `stage`, `#stage` carries `brightness(0.6)` at 23:00 and `#frame` carries none.
- `css/app.css` has no `transition` on `filter` and no `will-change: filter`.

- `formatRuntime(8040000)` is `2 h 14 m`, `formatRuntime(2880000)` is `48 m`, missing is empty.

### Fill modes

**R-FILL-1 (P2, U7) Landscape fill: blur and info panel.** `fillMode` (`none` default | `blur` | `info`). `blur`: a backdrop made from the current poster, downscaled once to a tiny canvas (48 px wide, which avoids visible banding at large scale) and scaled up by CSS (smooth upscaling is the blur; **no `filter: blur()` and no `backdrop-filter`**, which are expensive on a Pi GPU), dimmed to at most 25 % brightness for OLED safety. `info`: a side panel (title, summary trimmed to 300 characters, runtime, rating, year) beside the poster, shown only when the effective aspect is landscape and hidden when its box is narrower than 8 em of the title's font size (so 4:3 and 5:4 screens show the backdrop and no panel, D85); the panel keeps a top and bottom margin equal to its left gap (4 % of the screen's height), so a long synopsis never reaches the screen's edge, and the margin does not change which screens show the panel (D95); an episode shows its own synopsis, not the show's (D84). Both are off in portrait. Crossfade follows the poster. Multi-poster layouts are deferred (D1).
- 1920x1080, rotation 0, `blur`: `#fill-backdrop` exists with a canvas intrinsic width at most 64 px and effective brightness at most 0.25; no element has a computed blur `filter` or `backdrop-filter`.
- `info`: `#info-panel` shows title, runtime, rating, year and a summary of at most 301 characters; in a portrait viewport (or rotation 90 on a portrait screen that makes the effective aspect portrait) neither mode renders; `none` matches today.
- `isLandscape({w,h,rotation})` accounts for 90/270; `trimSummary(text, 300)` cuts on a word boundary with an ellipsis.

**R-FILL-3 (P2) Gap fill inside the frame.** `gapFill` (`none` default | `blur` | `matte`) fills the bands the poster image leaves inside the frame window (for example at fit "Fit inside window", or at a size below 100 %). `blur` reuses the R-FILL-1 technique (a tiny canvas of at most 64 × 128 px, scaled up by CSS, no `filter: blur()`): the poster sits on its own place in the canvas at its own size, and the poster's outermost row and column are stretched outward to the window's edge, so each band shows the poster's edge colours continued outward. A wide band shows no ghost, no copy of the poster's inner detail (its year, its ring), at any poster size or offset (D95). `matte` is one flat colour, the average of the poster's outer 2 %. Both are dimmed to at most 25 % brightness (the 0.25 cap of R-FILL-1). A gap under 4 px on its own is closed, not filled: the poster grows to the window edge (at "Fit inside window", evenly about its centre, or by a few pixels of crop when the box's own bands are that thin). A thin strip beside a wider band is filled with that band (D89). The fill cross-fades with the poster, and nothing of a blocked poster shows (D37); a poster whose edge cannot be read (cross-origin) gets no matte. D67, D89.
- `gapFill:'blur'` at fit "Fit inside window" shows the fill in the side bands at brightness at most 0.25 with no computed blur `filter`; `matte` draws the poster's edge colour, capped; a gap under 4 px with no wider band draws no fill; `none` matches today.

### Sleep and protection

**R-PROT-1 (P1, E1; D4) Sleep.** Two triggers, either sufficient: a daily schedule (`sleepEnabled` default **false**, `sleepStart`, `sleepEnd`; windows may cross midnight; device local time) and idle sleep (`idleSleepHours` > 0 hours with no playback; **0 = off, the default**; its help text says the screen stays black between movies). Asleep means: a pure black full-screen veil (`#sleep-veil`), controls and status hidden, poster fetches suspended (now-playing polling continues, at most every `nowPlayingPollSeconds`), and, when the device helper is on and available, display power off (R-HELP-2). **The screen wake lock stays held** while asleep so the panel stays lit and playback can wake it; releasing the wake lock is not used as a sleep mechanism, because re-acquiring a lock does not wake a screen the OS already blanked. The README tells Pi/Android users to turn OS screen blanking off. Wake: playback starts (`wakeOnPlayback`, default true, also during the scheduled window), the scheduled window ends, or a user touch/key/click (manual wake for 60 s, then back to sleep if the trigger still holds). On wake a poster is fetched at once. Schedules wait for a plausible clock (R-PROT-6).
- Pure state machine `decideSleep({now, settings, lastPlaybackAt, playingNow, manualWakeUntil, clockOk})` is unit tested: midnight-crossing windows, idle expiry at N hours, playback wake with `wakeOnPlayback` true and false, manual wake then back to sleep, `sleepEnabled:false` with `idleSleepHours:0` never sleeps, `clockOk:false` ignores the schedule but not idle sleep.
- E2E with a fake clock inside 01:00-07:00: `#sleep-veil` is visible and opaque black, controls hidden, `window.__wakeLock.held === true` with zero releases, no `/photo/:/transcode` request is made while asleep (counted with `page.on('request')`); `mock.play()` hides the veil within one poll interval and a poster is shown; idle sleep with `idleSleepHours:1` and 61 simulated minutes without playback sleeps; a key press wakes for 60 s then sleeps again; `wakeOnPlayback:false` keeps the veil during the window.
- Diagnostics shows the local time and `Sleep: awake|asleep (schedule|idle)`.

**R-PROT-2 (P1, E2; D6) Pixel shift with a glide.** The stage moves a few pixels every `pixelShiftMinutes` (default 3) along a fixed 9-point orbit that never repeats the same position consecutively. This requires a margin: when `pixelShift` is on (default **true**, D6) `stageSize()` sizes the stage to 97 % of the available box (a 1.5 % margin per side), giving about ±1.5 % of travel. The offset uses the individual `translate` property (composed before `rotate`, so it is in screen space at every rotation). Each step **glides** over 1.5 s (`transition: translate 1.5s ease-in-out`), not a jump, and the transition is removed under `prefers-reduced-motion`. Pure `shiftOffset(step, marginPx)` is unit tested.
- `shiftOffset` is bounded by the margin, never returns the same point twice in a row, visits 9 distinct points in 9 steps and is deterministic; `stageSize` with `margin: 0.015` is 97 % of the margin-less size on the limiting axis; without margin it equals today's output.
- With a fake clock and `pixelShiftMinutes: 3`, 20 steps at rotations 0 and 90 on 1920x1080 and 1080x1920 give at least 9 distinct `translate` values and stage and frame bounding boxes inside the viewport at every step (measured after the glide settles).
- `.stage` computes a `transition` that includes `translate` with a duration between 1 s and 2 s; with emulated reduced motion it does not.
- `pixelShift:false` leaves no `translate` and a stage equal to the margin-less size.

**R-PROT-3 (P1, E10; D6) Guarded daily self-reload.** `dailyReload` (default **true**) reloads the page at `dailyReloadTime` (04:00 local) and on the first wake from sleep if the last reload was more than 12 h ago, but never while settings or diagnostics are open and never during a fade. **Guard (D6):** the reload happens only when `navigator.serviceWorker.controller` is set **and** a `fetch('index.html', {cache: 'no-store'})` probe succeeds just before reloading (`sw.js` sends requests whose `cache` mode is `no-store` straight to the network instead of answering from the shell cache, so the probe really reaches the app server); otherwise it is skipped and the reason logged (an http LAN origin has no service worker, and a reload while the host is down would leave a dead browser error page). A guard against loops: `plexPoster.lastReload` is written before reloading and a second reload within 10 minutes is refused. Tablet note: in a browser tab (not an installed PWA) a reload drops Fullscreen API state, which needs a user gesture to re-enter; installed PWAs and `--kiosk` Chromium are unaffected, and the README says so. Schedules wait for a plausible clock (R-PROT-6).
- Fake clock 03:59:30, service worker allowed: a reload happens at 04:00; none while Settings or Diagnostics is open (retried after close); `dailyReload:false` none; with the **app server** unreachable at 04:00 (probe fails; the spec stops its own `serve.mjs` child, or aborts the probe with an offline emulation that also covers service-worker fetches; never `mock.down()`, which only stops the Plex mock) none and a logged skip; with service workers blocked (no controller) none and a logged skip.
- On wake from sleep with `plexPoster.lastReload` older than 12 h exactly one reload, newer none; after a reload settings persist and `paused` is cleared.
- A `fetch('index.html', {cache: 'no-store'})` from a page controlled by the service worker is served by the network: it fails when the app server is stopped, and `sw.js` still serves the cached shell to ordinary requests and navigations when it is.
- Diagnostics shows `Daily reload: active|skipped (reason)`.

**R-PROT-4 (P1, E9) No expensive compositing.** Remove `backdrop-filter: blur(8px)` from `.sheet` (replaced by a slightly more opaque panel). No rule may use `backdrop-filter`; no `filter` is animated or transitioned (brightness changes are stepped, R-FRM-4). Also `overscroll-behavior: none` on `html, body` (sceptic M9) as the in-page backstop for swipe-back (R-DOC-4).
- `css/app.css` contains no `backdrop-filter` and no `will-change: filter`.
- `html` and `body` compute `overscroll-behavior: none`.

**R-PROT-5 (P1; D4, D5, D6) Recommended protection preset.** One button in Settings > Display protection applies: sleep schedule on 01:00-07:00, night dim on at level 60 with target `stage` (Q20), pixel shift on, daily reload on. It shows what it will change before saving. **It does not turn on idle sleep (D4) and does not set a content limit (D5).** It never touches the connection, `maxContentRating` or `limitNowPlaying`.
- Clicking it lists the keys it will change; Cancel changes nothing; Apply then Save persists `sleepEnabled:true`, `sleepStart:'01:00'`, `sleepEnd:'07:00'`, `nightDim:true`, `nightDimLevel:60`, `nightDimTarget:'stage'`, `pixelShift:true`, `dailyReload:true`.
- `idleSleepHours`, `maxContentRating`, `limitNowPlaying`, `plexToken`, `serverUrl` and `libraryKey` are unchanged after Apply.

**R-PROT-6 (P1, sceptic M4/M5) Schedules wait for a plausible clock and survive DST.** A Pi has no RTC: until NTP syncs, local time can be years off. `isPlausibleClock(date)` is true for a year of 2026 or later (Q23); until it is true the sleep, night-dim and daily-reload schedules do nothing and Diagnostics says `Clock not set`. The schedule helpers (`inWindow`, `msUntilNext`) are correct across daylight-saving changes: a window of 01:00-07:00 on a change night, and a 02:30 job on a spring-forward night (the time does not exist) and a fall-back night (it occurs twice).
- Unit tests, run with `TZ=America/New_York` and `TZ=Europe/London`: simulating 400 consecutive days of fire-and-re-arm with `msUntilNext`, every local date fires exactly once for `04:00` and for `02:30`, `msUntilNext` is never negative or NaN, and `inWindow('01:00','07:00')` is true at 01:30 on both occurrences of 01:30 on a fall-back night.
- `isPlausibleClock(new Date(1970,0,1))` is false and `isPlausibleClock(new Date(2026,9,8))` is true.

### Device helper

**R-HELP-1 (P1, E6; D8) Optional Pi helper: power and temperature.** `scripts/device-helper.mjs`, mounted by `scripts/serve.mjs --helper`, provides what a page cannot: **screen power and CPU temperature**. Brightness control is dropped (D8: consumer TVs rarely implement DDC/CI and HDMI outputs have no backlight sysfs). All endpoints are under `/__helper/`, answer only loopback peers whose `Host` hostname passes `isLoopbackHost` (R-SEC-1), require the custom header `X-Poster-Helper: 1` (forces a CORS preflight that is never granted, so other websites cannot drive it), and never use a shell (`execFile` with fixed argument arrays and validated boolean inputs). The helper is loopback-only and opt-in (`--helper`). Power strategies, each detected at start and overridable by flags **(verify all on hardware)**:
- `cec-ctl` (v4l-utils, `/dev/cec0`, needs the `video` group): `cec-ctl -d /dev/cec0 --to 0 --standby` and `--image-view-on`.
- `cec-client` (libcec): `standby 0` / `on 0` through stdin.
- `wlr-randr --output <name> --off|--on`, run with the compositor environment passed through: `WAYLAND_DISPLAY` and `XDG_RUNTIME_DIR` taken from the helper's own environment or from `--helper-wayland-display` / `--helper-xdg-runtime-dir` (a `systemctl --user` service starts outside the compositor session and has neither).
- Temperature: `/sys/class/thermal/thermal_zone0/temp` divided by 1000 (`vcgencmd measure_temp` as fallback).
- `GET /__helper/status` returns `{power, temperature, tempC}` where `power` is the chosen strategy or `null`. A fake mode (`--helper-fake`) returns canned values, records calls for tests and lists them at `GET /__helper/calls` (fake mode only; 404 otherwise, same guards). Documented in the README.
- A non-loopback peer, a missing header, a hostile Host or a non-boolean `on` gets 403/400 and runs no command (asserted with an injected fake `execFile`); a bad `X-Forwarded-For` has no effect.
- `POST /__helper/brightness` does not exist (404).

**R-HELP-2 (P1, E6, E9) Integration and temperature.** `js/helper.js` probes `/__helper/status` at boot (404 or network error means "no helper", silent); when `deviceHelper` (default false) is on and the helper exists: sleep calls power off after the veil is up and power on before the poster fetch on wake (R-PROT-1), and Diagnostics shows "CPU temperature". All of it no-ops on static hosting. A V1-extended row checks that after power off then on the window is still full-screen and playback wakes within a bounded time (a power cycle can renegotiate the display and hide the page).
- A 404 or network error gives `available:false` without throwing; every request carries `X-Poster-Helper: 1`; failures are logged once, not every tick.
- With `--helper --helper-fake`, entering sleep makes `GET /__helper/calls` show power off and waking shows power on; with `deviceHelper:false` or no `--helper` the page makes no `/__helper/` request after the initial probe and logs no console error.

### Kiosk

**R-KIOSK-1 (P1, E12; D10) Kiosk mode, PIN and recovery.** `kioskMode` hides the controls entirely (they are `inert`, so Tab cannot reach them): pointer movement and taps never reveal them. Two reveals work: a 3-second press-and-hold in the **bottom-right corner as the viewer sees it** (a 96x96 px zone mapped through `rotation` when `rotateUi` is on), and **holding OK/Enter for 3 s** (for D-pad remotes); either reveals the controls for 15 s, and both still work when `disableShortcuts` is on. `settingsPinHash`/`settingsPinSalt` hold a salted SHA-256 (Web Crypto; fallback to a plain pure-JS hash when `crypto.subtle` is unavailable on an insecure origin). When a PIN is set it is required to open Settings, Diagnostics, reset, import, and Show token. Five wrong tries lock for 60 s (doubling to 15 min). `disableShortcuts` ignores all keyboard shortcuts including `?`. **A PIN is a deterrent against children and visitors, not authentication; anyone with browser devtools or filesystem access can bypass it, and the UI and README say so (D16).**
**PIN recovery (D10):** on every load the app fetches `config.json` (served to loopback clients only, R-SEC-1); if it contains `"resetPin": true` the stored `settingsPinHash`, `settingsPinSalt` and the lockout are cleared. A non-loopback client never receives `config.json`, so a PIN cannot be reset over the network. Diagnostics shows `PIN reset flag present` while the flag is in the file, and the README says to remove it afterwards (Q21).
- Unit tests: hash/verify with salt, lockout schedule, corner-zone mapping at all four rotations, hold timer cancelling on movement over 12 px or early release.
- E2E: in kiosk mode `pointermove`/tap/key never adds `.visible`; a 3 s hold in the corner does, for 15 s, at rotation 0 and 90; a 3 s Enter hold does, also with `disableShortcuts:true`; with a PIN set, `s` and the Settings button show the PIN dialog (on-screen keypad usable by touch; at rotation 90 `#pin-dialog`'s computed angle is 90 and its box lies inside the viewport); a wrong PIN keeps Settings closed; the correct PIN opens it.
- With a PIN set and `config.json` intercepted by `context.route` to return `{"resetPin": true}`, after load Settings opens without a PIN and the PIN material is gone from `localStorage`; without the flag the PIN stays.
- Export never includes `settingsPinHash`/`settingsPinSalt` even with "include token" ticked, and an import file containing them is ignored.

**R-KIOSK-2 (P1, E16) Show token behind the PIN.** `#token-toggle` ("Show") requires the PIN when one is set; it re-hides the field when the sheet closes.
- With a PIN set, pressing Show opens the PIN dialog; a wrong PIN leaves the field masked; the correct PIN reveals it; closing the sheet masks it again.

### Content filter

**R-FILT-1 (P1, E14; D5) Maximum content rating.** The limit is a "Household with children" toggle in Settings (UI-only: on reveals the rating select defaulting to `PG-13`, off stores `maxContentRating: ''`); it is **not** part of the protection preset. `maxContentRating` (`''` = no limit; `G`, `PG`, `PG-13`, `R`, `NC-17`) applies to:
- **random posters** (pool loading) — request-side Plex `contentRating` filter **(verify parameter name, multi-value syntax and normalisation)** whose value list contains every ladder value at or below the limit **and** every mapped country-prefixed value at or below it (so `PG-13` sends `G`, `PG`, `PG-13`, the `TV-` equivalents and `gb/U`, `gb/PG`, `gb/12`, `gb/12A`, `de/0` and the rest of the table), plus a client-side filter that is the guarantee;
- **cached (offline) posters** — `js/poster-cache.js` index entries gain `contentRating`, and `cache.random()` skips entries above the limit; entries without a stored rating (cached before 2.1) are skipped while a limit is set;
- **now-playing** — when a limit is set and `limitNowPlaying` (default **true**, switchable) is on, a playing item above the limit (or unrated) is treated as nothing playing and the display shows a random allowed poster.
An **owner-pinned** poster is exempt. Client-side ladder: `G=TV-Y=TV-G < PG=TV-Y7=TV-PG < PG-13=TV-14 < R=TV-MA < NC-17`. Country-prefixed values map onto that ladder (table below, Q19); **unrated, missing and unmapped values are excluded while a limit is set**. Because filtering shrinks the pool, the request oversamples (size x3, cap 500). The pool cache key includes the limit; an empty result produces the existing "No posters found" error with a hint to raise the limit.

|---|---|
| `gb/` | `U`=G, `PG`=PG, `12`/`12A`=PG-13, `15`=R, `18`=NC-17 |
| `de/` | `0`=G, `6`=PG, `12`=PG-13, `16`=R, `18`=NC-17 |
| `au/` | `G`=G, `PG`=PG, `M`=PG-13, `MA15+`=R, `R18+`=NC-17 |

- Unit tests over every ladder rung, every table row, the request value list (every allowed ladder value and every mapped prefixed value at or below the limit, nothing above), an unmapped prefixed value (`gb/XX`), unrated, missing, the oversample size, the pool cache key, the cache-index skip, and the now-playing rule (above limit, unrated, `limitNowPlaying:false`, pinned exempt).
- Against the mock (its 8 titles carry G, PG, PG-13, R, TV-MA, `gb/12`, `gb/15` and no rating, and it honours the filter parameter as a list), a PG-13 limit shows only the G, PG, PG-13 and `gb/12` titles across 50 picks (never R, TV-MA, `gb/15` or the unrated one); under `R` the R and TV-MA titles also appear (same rung); with no limit all 8 appear. NC-17 is covered by the unit tests.
- A cached R poster is never shown by the offline fallback under PG-13, and a playing R title under PG-13 is not displayed (the next random allowed poster is).
- The preset (R-PROT-5) leaves `maxContentRating` and `limitNowPlaying` unchanged.

**R-FILT-2 (P1; D59, D101, D103, D104, D105, D106, D117) Content limit by time of day.** A household can set up to 8 time slots, each with its own limit, for example G from 06:00, PG-13 from 15:00 and no limit from 22:00. The slots live in Settings > Household beside the limit, in a "Change the limit during the day" editor (a start time, a limit or "No limit", and Every day, Weekdays or Weekends for each slot; Add and Remove). The key is `limitSlots`, a list of `{ start: 'HH:MM', limit, days? }` (`limit` is `''` for no limit or one of the R-FILT-1 values; `days` is a list of weekdays, 0 = Sunday, and absent means every day). A slot gives a limit or, with `profile` (a profile id) in place of `limit`, names a viewer profile and takes that profile's limit (R-PROF-1). `js/limit-schedule.js` holds the one function, `limitInForce(settings, date)`, that says which limit applies at a moment (`slotInForce` also says which slot gave it), and `js/profiles.js` builds the settings in force on it (R-PROF-1). Every reader of the limit calls it, or the resolver: the engine (the pool request, the pool cache key, the cached-rating re-check, the permit test and the empty-card advice), the offline cache fallback, the check on what is on screen and the empty-card wording. `maxContentRating` is only the base limit.
- **The slot in force (D103, D105).** A slot applies only on the days in its set (no set means every day). On a day, the slot in force is the one with the latest start at or before the time among the slots that apply that day. Before that day's first applicable slot (D105, D106 5): the slots in force at the end of the previous day (the latest start among that day's slots; the stricter of two at the same start) run on only when every one of them also applies today (a slot runs until the next one starts); otherwise the latest-starting of the previous day's slots that also apply today carries over (the stricter of two at the same start) but never looser than the base limit (`maxContentRating`); and when there is none, the base limit applies. So with a base of G, "PG-13 from 22:00 every day" and "No limit from 22:00 Sundays", Monday 03:00 is G: Sunday's no-limit slot does not apply on Monday, so the pair does not run on, and the PG-13 slot that does is capped at the base. In the repeated hour of a fall-back clock change a slot that has started does not stop applying. So a "no limit from 20:00, Weekends" slot under a PG-13 base gives no limit on Saturday and Sunday evenings and on Sunday morning, and PG-13 on a Monday; and with a base of R, an every-day "G from 06:00" slot plus a weekend-only "PG-13 from 20:00" slot still gives G on Monday at 03:00 (the weekend slot does not apply on Monday, the every-day one does). Two slots at the same start: the stricter one. With no slots the limit is `maxContentRating`, as in 2.2 (a 2.2 display behaves as before). With the household toggle off no limit applies and saved slots (and profiles) are kept but not applied.
- **Fail closed (D5, D103).** A clock that is not set (`isPlausibleClock` false) gives the strictest of the base limit and every slot (a slot that names a missing profile counts as `G`) and, while any slot names a profile, every profile (R-PROF-1). The sanitiser turns a slot with an unknown limit into `G`. A schedule with ANY slot whose time is unreadable (in `config.json`, an import file or a stored value) reads as `G` all day: no slot is dropped for its time, because dropping a stricter slot could loosen the schedule. A schedule that is not a list reads the same way, and an unreadable weekday set makes the slot apply every day at `G`. A schedule with more than 8 slots reads as `G` all day (D105). The editor refuses Save, with a message beside the row, while any slot's time is empty or unreadable. Unrated titles stay hidden in every slot that sets a limit (R-FILT-1). A pinned poster stays exempt, and now playing follows `limitNowPlaying`, both as in R-FILT-1. An absent `maxContentRating` is read as the settings default, `''`.
- **The editor says what applies (D103).** A line under the editor shows the limit in force now and until when ("In force now: G until 15:00.", "In force now: No limit until 06:00."; with the toggle off, that no limit applies and the slots are kept). A change a week away says "until next Mon 08:00" (D106 4), and in the repeated autumn hour it never names a time already past (D106 2). The line is a live region and is written only when its words change, so a screen reader does not say it again every second (D106 3). It starts "Saved:" (it describes the saved settings, not unsaved edits), shows with the household toggle off too, and updates while the sheet is open. When a start time falls in the spring-forward gap it names the real change time (03:00, not 03:30). The footer message about a missing start time goes when the time is fixed or the row removed. The slot limit list uses the same labels as the main limit list, each Remove button names its slot ("Remove the 06:00 slot"), and the time field's clock icon shows a focus outline. The online empty card's advice names the time slots while any exist. The D37 re-check of cached ratings runs whenever the base limit or any slot sets a limit. A line under the "Household with children" toggle, shown whether it is ticked or not, reads "The rating limit, the times it changes during the day, and viewer profiles are set here." (D126 3, D128 3). Ticking the toggle keeps it where it was on screen, so the schedule and the profiles come into view below it (D128 1); the toggle is never ticked by itself. When the stored or imported schedule was unreadable and so reads as `G` all day, the editor says so above the slots until the slots are edited, and a Save keeps `G` all day as the owner's schedule (D132). While a pinned poster is saved and a limit is set, the status line adds that the pinned poster stays up whatever the limit (D132).
- **Changes on screen at the boundary.** A one second check follows the clock (sleep, wake, a hidden tab and clock jumps need no timer to re-arm). When the limit in force changes, a poster the new limit does not allow comes off at once (`blockPoster`, as a Save does) and a forced tick draws the next poster under the new limit, with no Save and no reload. A boundary replaces the poster on screen only when it is no longer allowed (D105): an allowed poster stays, a paused display keeps it, and a looser limit takes effect at the next rotation. A tick already running when a boundary takes the poster off is followed by a forced tick.
- **Applied on Save only, never live-previewed.** The slots are in the preview carve-out with `maxContentRating` and `profiles`; Cancel restores them. Opening Settings behind the PIN is the gate; there is no per-field gate. A Save that changes the limit in force forces a redraw once.

**R-SEL-1 (P1; D60, D63, D101, D107) Poster selection.** The random pool can be any chosen movie libraries, narrowed to chosen genres and chosen ratings, or one Plex collection (smart or not) or one playlist, and the household limit (or the slot in force, R-FILT-2) is still the ceiling (D5). The controls are in Settings in their own "Poster selection" section after Connection: the movie libraries as checkboxes (each with its title count, as the library list showed it), a "Posters from" list (the libraries above, or one collection or playlist the server lists), the genres of the ticked libraries as checkboxes in a box that scrolls (ticking one keeps keyboard focus and the scroll position), and the ratings. The "Connected to" line names the source while one is chosen. A collection or playlist is enough to Save: no library need be ticked. `js/selection.js` holds the pure rules; the engine, the offline cache and Settings all call them.
- **Source (D107 ruling 1).** The source is the chosen libraries, or one collection or playlist, which replaces them: its items are the pool, the genre set is not applied to it and the genre list is disabled while it is chosen. The genre ticks stay shown and are kept on Save while a source is chosen (D112 item 3): the engine ignores them there, and choosing "The libraries above" again brings them back. The rating subset and the limit in force apply to every source. The libraries stay stored (and ticked, disabled) so removing the source brings them back.
- **Ratings never widen (D5).** The ratings offered in Settings are every rating up to the loosest limit of the base limit being edited and every time slot (D109), all five while the toggle is off, so a household can narrow a looser evening slot to its own higher ratings; ticks are kept on Save. A chosen subset is intersected with the limit in force, not the base `maxContentRating`: with G, PG and R chosen under a PG-13 slot only G and PG remain; the engine's intersection is with the limit in force at draw time, so at noon under a PG-13 slot an R title is never drawn even though R was offered and ticked. One the limit leaves empty asks Plex for nothing and shows the empty card. A title is drawn only if its own rating passes the limit and is on a chosen rung (country-prefixed values by the R-FILT-1 table); an unrated title is never drawn under a limit or a subset.
- **Server filters are only a convenience.** Plex is asked for `genre=<filter keys, comma separated>` and `contentRating=<values of the chosen rungs>`, and the client then checks every reply on the item's own `Genre` tags and rating, so a server that ignores a parameter cannot widen the pool. A reply item with no genres is not drawn while a genre is chosen. With "unwatched only" on, a collection's or playlist's items with a `viewCount` are left out. Its items are ordered best rated first and cut to the pool size (3 times that, at most 500, under a limit or a rating subset, as a library is asked for, because they are cut again afterwards).
- **Several libraries (D107 ruling 3).** Each chosen library is asked for posters; the pool size setting is the total, split in proportion to the libraries' title counts (the size-0 count request, largest remainder). A count that cannot be read, or counts that are all zero, split it evenly; a library with no share is not asked. A library whose count is above zero always gets at least one slot (D112 item 2), taken from the largest share, as far as the pool size allows; the shares are otherwise proportional. One library is asked for the whole size and no count, exactly as in 2.2.
- **Migration (D107 ruling 2).** Settings saved before 2.3 with only `libraryKey` load as that one library: `libraryKeys` is `[libraryKey]`, with no genres, no rating subset and no source, and nothing else changes. `libraryKey` and `libraryName` always mirror the first chosen library, so everything that reads one library keeps working. A file (a hand-written one, an import) that sets only `libraryKey` replaces the whole selection: that library, no genres, no rating subset, no source. An XML reply keeps the `Genre` tags like a JSON one.
- **Offline (D107 ruling 4).** A cache entry records `libraryKey`, the title's `genres` and the `members` (`collection:<id>` or `playlist:<id>`) it was listed in, written when the poster is cached and when it is seen online again. While the selection narrows the pool (more than one library, any genre, any rating subset, a collection or a playlist) a cached poster is drawn only if its entry records that it belongs, and the limit in force still applies; an entry without those fields is never drawn. Memberships accumulate (a title can be in several collections and playlists), and when a collection's or playlist's whole listing is loaded online, cached entries that are no longer in it lose that membership. With the 2.2 selection (one library, nothing else) the cache behaves as before.
- **After a Save that matches nothing (D110).** When the saved selection draws nothing (an "empty" result, not a failed request), the empty card naming the selection shows if the poster on screen no longer matches it (another library, genre or rating, outside the collection or playlist, above the limit in force); a poster that still matches stays, and a pinned or now-playing poster is not judged. A collection or playlist drops what the limit in force or the chosen ratings reject before it is cut to its size, and the full listing still updates the offline memberships. With several libraries and one failing, the pool comes from the others; only all failing is a failure, and so is one failing while the others answer with no posters at all (D112 item 1): the first failure is reported as a connection problem, not this card, because its advice to loosen the selection would not help. The empty-card advice is one sentence and suggests "add a library" only when the server has a movie library that is not ticked. A stored rating tick above the offered range is kept on Save and shown as a ticked row marked "above the limit now", which the parent can untick (D111 item 1). When a library fails among several, the reduced pool is kept for a minute (not the pool's 30 minutes) before the full selection is asked for again (D111 item 3).
- **Counts (D107 ruling 5).** The library checkboxes show the plain library count only; no "N titles match" count is shown, because the size-0 request ignores filters.
- **Empty result (D107 ruling 7, D109 item 3, D110 item 4, D111 item 2).** A selection that matches nothing shows the empty card naming it, then one sentence of advice in brackets, its parts joined by " or ", in this order: `try turning off "unwatched only"` (while it is on); `raise the limit` (`raise the limit or change the time slots` while slots exist) while a limit is in force; then, only while the selection narrows, the widening advice. Libraries: `add a library`, only when the server lists a movie library that is not ticked (asked once, on this path; a failed or missing answer leaves it out), then `tick fewer genres`, `tick fewer ratings` or `tick fewer genres or ratings` for what is ticked. A collection or playlist: `use the libraries instead of the collection` (or `playlist`), then `tick fewer ratings` when ratings are ticked. Examples: "No posters found in Movies, genre Western (add a library or tick fewer genres)."; "No posters found in the collection "Top Rated", rated G at or below PG (try turning off "unwatched only" or raise the limit or use the libraries instead of the collection or tick fewer ratings)." The 2.2 selection still says "that library" and gets no widening advice.
- **Applied on Save only (D101 ruling 6).** The selection keys are in the live-preview carve-out with the limit; Cancel restores them; a Save that changes the selection forces a redraw. The Plex request shapes the research could not confirm are (verify) rows in the extended validation file (section H), among them whether a library list reply carries every `Genre` tag of a title.

**R-SEL-2 (P1; D64, D101, D112, D113, D114, D115, D116) Weighting and the no-repeat window.** The random pool can lean toward unwatched or highly rated titles, and a title once shown stays away for a chosen number of days, remembered across reloads. Two controls sit in Settings under "What to show", after "Random posters: unwatched only": **Favour in random posters** (nothing, unwatched titles first, best reviewed first by audience score) and **Keep a shown poster away for** N days (0 to 30, 0 = off). `js/weighting.js` holds the pure rules; the engine calls them. Both apply on Save and take effect from the next draw, with no reload. Neither is live-previewed: they join the preview carve-out in js/main.js with the limit and the selection (D114 1), so an unsaved value never reaches the engine and an unsaved window of 0 seen through another control's preview does not clear the saved record; Cancel leaves it intact (D116 1). While a slot names a viewer profile, the profile's weighting and window replace these (R-PROF-1); one record serves every profile.
- **Defaults change nothing (D101 ruling 5).** Weighting off and window 0 draw exactly as before: every permitted title weighs 1, the last 10 shown are avoided, and nothing is stored. The same random numbers give the same draws.
- **Weights (D113 ruling 1).** Unwatched first: 3 for a title with no `viewCount` (or 0), 1 for a watched one. Best reviewed first (audience score): 1 plus the title's `audienceRating`, or its `rating` when that is absent (read as 0 to 10), so a higher rating is drawn more often; a title with neither gets 1, the lowest. The poster descriptor carries `viewCount` (only when above 0), `audienceRating` and `rating` when the server sent them.
- **A ceiling, not a door (D5).** Weighting and the window only reorder chances inside the permitted pool: the draw starts from the titles the limit in force, the rating subset and the genres allow. Nothing here lets in a title they exclude.
- **The history of 10 (D113 ruling 2).** With weighting on, the last-10 rule does not apply (it cancels the weight on a small pool): the draw is weighted over the permitted pool minus the poster on screen and minus the titles inside the window. A window above 0 replaces the last-10 rule, with weighting on or off.
- **The window (D113 ruling 3).** Whole days, 0 to 30. The time each title was last shown is kept in the display's own storage (`plexPoster.shownAt`), not in the settings, so it is never exported; it survives a reload, entries past the window are pruned, and a value that cannot be read starts it empty. With the window at 0 nothing is recorded, and the record is removed from storage when it is there and no profile has a window above 0 (a draw, a shown poster or a Save with the window at 0 does it; D120 5), so 0, Save, 3, Save before any poster shows starts empty (D114 2, D115 4, D116 2). A title shown within the window is left out of the draw; when every permitted title is inside it, the one shown least recently is drawn. A cached poster shown while offline is recorded too.
- **Offline (D113 ruling 4).** Draws from the poster cache are unchanged and unweighted.
- **Unwatched only (D113 ruling 5).** "Unwatched only" is on by default, so the pool holds no watched title and "unwatched first" changes nothing until it is turned off. The help text under the controls says so.
- Unit tests (seeded random): off draws as before for the same random numbers; unwatched first over 2,000 picks draws an unwatched title at least twice as often as a watched one; best reviewed first rises with `audienceRating` and with `rating` when it is absent; the window keeps a shown title out across a simulated reload, falls back to the least recently shown, and prunes; a corrupt value starts the record empty; the limit, a rating subset and a genre set still exclude; the sanitisers; the poster descriptor fields; the three D112 items.

**R-PROF-1 (P1; D101, D117, D119, D120) Viewer profiles.** A household can save named profiles (for example Kids, Teens, Adults), each a bundle of a household limit, the now-playing rule, a poster selection, weighting and a frame, and a schedule slot can name a profile instead of a bare limit. `js/profiles.js` holds the pure rules and the one resolver, `resolveSettings(settings, date)`, that gives the settings in force at a moment: the stored settings with the in-force profile's bundle laid over them and `maxContentRating` set to the limit in force (`limitInForce`). The engine, the offline cache fallback, the check on what is on screen, now playing, the frame, the empty card and the status line read it, as they read `limitInForce` before profiles (R-FILT-2). The limit in force is a ceiling and always wins (D5): nothing in a bundle can raise it.
- **What a profile holds (D117 1).** `{ id, name, maxContentRating, limitNowPlaying, libraryKeys, libraryNames, genres, ratings, source, weighting, noRepeatDays, frameId }` and nothing else. The name is 1 to 24 characters after trimming and unique ignoring case. At most 6 profiles; a 7th is refused. The key is `profiles`, default `[]`: an upgrade, and any display with no profile and no profile slot, behaves exactly as before (D101 ruling 5). An unknown or absent limit in a profile is `G`, never no limit; `limitNowPlaying` omitted is on; the other fields are cleaned like the sheet's own values. A stored or imported list drops a profile with no id or readable name, a repeated id, a name that repeats an earlier one ignoring case (the duplicate is dropped, not renamed), and any beyond the sixth.
- **The editor (D117 2, D120 1).** In Settings > Household, beside the slot editor, a "Profiles" group lists each profile with its name ("Profile name", editable; Enter or leaving the box renames it in place, the rows are not redrawn, so focus stays and a click on another row's button is not lost), a one-line summary (limit, library or source, frame, and the weighting when it is on), "Edit" and "Delete". A name box and "New profile" open a new profile. "New profile" and "Edit" open the profile in the sheet: a banner at the top names it, the bundled controls (the limit, the now-playing rule, the poster selection, weighting and days, the frame) show the profile's values, and the household's own values are set aside. The limit list also offers "No limit" while a profile is open. "Done" writes the bundle into the profile and puts the household's values back; "Discard" puts them back with no change; Save and Cancel are not offered while a profile is open, and a whole-sheet Cancel (Escape) still restores everything. "Done" is refused, in words in the banner, while the profile ticks no library and has no source, as the sheet's own Save is. Editing a profile never changes the household's own values, and nothing a profile holds is previewed on the display. A refusal (an empty, long or duplicate name, a 7th profile, a deletion a slot blocks) is said in words beside the group. Everything applies when Save is pressed and Cancel restores; Enter in a name box never saves the sheet. The name boxes read "Profile name" and the profile help is linked to the editor's fields with `aria-describedby`. Each slot's choice list gains the profiles ("Profile: Kids") after the limits; a slot gives a limit or a profile, not both. The help says that while a slot is in force the profile's settings replace the household's, its limit too, even when the profile's limit is looser, and that the status line under the slots says which limit is in force. The banner names everything the profile holds (the limit, the now-playing rule, the selection, the weighting and days, the frame). "Done" says "<name> kept; it applies when you press Save." in a polite live region. The banner and the rows name the profile as it is now, after a rename in the same row. The genre list follows the libraries the controls show: opening a profile, "Done" and "Discard" each drop a genre load in flight and load the genres of the libraries now shown. While a profile is open the household's live controls (the poster size and position, brightness, the non-bundled ones) keep previewing; nothing the profile holds is previewed, and "Done" and "Discard" send one preview.
- **A slot names a profile (D117 3).** While a slot that names a profile is in force, that profile's bundle replaces those settings and the limit in force is the profile's `maxContentRating`. Carry-over, the fall-back hour and the stricter of two slots at the same start (R-FILT-2) work as for a limit, using the profile's limit; of two equally strict, the first listed supplies the bundle. Outside every slot the sheet's own values apply. The status line names the profile ("In force now: G (Kids profile) until 21:00.").
- **Fail closed (D5, D120 2).** A slot that names a profile that does not exist (an import, a stored value) is read like an unreadable slot: `G`, the strictest value, while that slot would be in force (including a carry-over from it), whatever the base limit or any other profile holds; no bundle is laid over, so the other settings are the sheet's. The sheet shows that slot's choice as "Profile: missing" and, while it is in force, the status line says the profile does not exist and G applies. An implausible clock gives the strictest limit among the base limit, every slot (a missing profile counts as `G`) and, while any slot names a profile, every profile; no bundle is laid over. An unreadable schedule is still `G` all day (D102); a profile slot with unreadable weekdays becomes a plain `G` slot.
- **Deleting a profile a slot names (D117 6).** Refused, and the editor says which slot ("Kids is used by the 06:00 slot. Change or remove that slot first.").
- **A boundary that changes the profile (D117 7, D120 6).** The one second check (R-FILT-2), which reads the clock and the settings once per check, also notices a change of profile. A poster the new profile does not allow, by the limit or by the selection, comes off at once (within 2 s, before the page asks for anything) and a forced tick draws the next under the new profile; a poster it allows stays. A poster whose draw finishes after a boundary is checked against the selection in force when it is shown, not only the limit. The new frame applies without a reload and the new weighting and window apply at the next draw. The pool reloads when the selection changes (the pool key follows the selection in force). A pinned poster (the one the Pin button pinned, even though it was drawn at random) stays exempt from the limit and the selection, online and offline, and a now-playing poster is not judged by the selection (R-FILT-1).
- **The household toggle (D120 4).** With the household limit off ("No limit" base) the slots and profiles are kept and not applied, as R-FILT-2 says: no limit applies and no profile switches anything (not its selection, weighting, frame or now-playing rule). The editors are hidden while it is off, and the status line says the slots and profiles are kept, not applied.
- **A profile that chooses nothing (D120 3).** A stored or imported profile that ticks no library and has no source, while it is in force, makes the engine report an empty result naming it ("The profile “Kids” has no library or collection chosen. Edit it in Settings."), shown on the empty card: never a silent blank, and nothing is asked of the server.
- **One shown-titles record (D120 5).** All profiles share the record of R-SEL-2. A profile with a window of 0 records nothing and clears nothing; the record is cleared only when the household's own saved window is 0 and no profile has a window above 0.
- **Export and import (D117 9).** Profiles and the slots that name them are exported and imported with the settings; an imported profile is cleaned like the sheet's own values (names cut to 24; a later duplicate (ignoring case) is dropped; a 7th dropped; an unknown limit `G`). PIN material is never exported or imported (D5).
- **Applied on Save only (D101 ruling 6).** `profiles` is in the preview carve-out with the slots; Opening Settings behind the PIN is the gate, with no per-field gate. A Save that changes the selection in force forces a redraw.

**R-SRC-1 (D134) Source adapters.** The engine, the display, Settings and the first-run card talk to a media server only through the object `createSource(settings)` returns (`js/sources/index.js`); nothing outside `js/sources/` imports an adapter. The adapter has `label` (the server's name as people read it: "Plex") and the methods `identity`, `libraries`, `libraryCount`, `sessions`, `pool`, `sourceItems`, `genres`, `collections`, `playlists`, `item`, `items`, `imageUrl` and `nowPlaying`. The setting `serverType` picks the adapter; absent, as in a 2.3.1 settings object, it is `'plex'`. A type with no adapter makes `createSource` throw a `SourceError` of kind `config`; every other adapter error keeps the kinds `network`, `timeout`, `auth`, `http` and `parse`. Items keep their server's own ids: the poster cache, the pinned poster and the no-repeat history store them as they are, and keys written by 2.3.1 read as Plex entries with no migration. A server-side rating filter is an optimisation only: every poster from any adapter still passes the household limit in the engine (D5).

**R-SRC-2 (D134, D139, D141) Jellyfin as a source.** A household with a Jellyfin server picks Jellyfin as the server type, signs in with a Quick Connect code (or a user name and password), chooses movie libraries, genres, ratings, a collection (a BoxSet) or a playlist, and gets the same display, now playing, limit, schedule, profiles and weighting as a Plex household. The adapter is `js/sources/jellyfin.js`; every rule below is tested against the mock server (`scripts/mock-jellyfin.mjs`), and every request or field the mock invents is a (verify) row in `docs/validation/real-server-extended.md` section I.
- **Server type.** `serverType` is `'plex'`, `'jellyfin'` or `'emby'`. The first-run card and the Settings sheet offer the choice; the words that name the server ("Jellyfin" for a Jellyfin household, the 2.3.1 words for Plex) follow it. A value this build has no adapter for is kept as written, never turned into Plex: the display shows the empty card with "Unknown server type "<type>"." and makes no request. A missing `serverType` is `'plex'` and is not a switch.
- **Switching.** Saving a different `serverType` (a missing one counts as Plex; an import is a Save) clears the offline poster cache, the pinned poster and the no-repeat history (with several servers, only the first server's own entries, R-SRC-4). Choosing a type in the form, signing in and Cancel clear nothing. Stored ids are not translated, and there are two routes. A switch made in the sheet and followed by a connection test re-picks: the sheet's `offerLibraries` drops the library keys the new server does not list and, with none left, ticks the first movie library; the household chooses genres, collection and playlist again from the new server's lists. An import (or a hand-edited file) followed by Save with no connection test keeps the library, genre, collection and playlist ids as stored: they match nothing on the other server, so the pool is empty and the empty card says so (fail closed). The profiles and the slots keep their ids on both routes. A Save that changes the server type says so in the toast, in one sentence naming the new server: "Now showing posters from Jellyfin. The offline posters, the pinned poster and the no-repeat history were cleared." (a Save that changes nothing about the type still says "Settings saved."). Changing to another server of the same type clears nothing (the cached posters still pass the limit in force, D37) until its id is recorded; after that R-SRC-4 decides by the server's id. The token and address follow the type on every route into the sheet: the choice of a type, an import (a file for another type brings its own token and address, or none, and the old ones are set aside; a file that names a connection but no server type is a 2.3.1 Plex file) and the first-run card's choice (handed to the sheet with the earned token, and kept by Open settings). A Plex token is never sent to a Jellyfin server, nor a Jellyfin token to a Plex server. Changing the type in the sheet drops a connection test still in flight: its late answer is not shown.
- **Signing in.** The server address comes first (the first-run card and the sheet ask for it). Quick Connect asks the server for a six-digit code (`/QuickConnect/Initiate`), shows it large and upright, polls `/QuickConnect/Connect` and signs in with `/Users/AuthenticateWithQuickConnect`. A code the server no longer knows (404) offers a new one. Only a server that answers `/QuickConnect/Enabled` with `false` gets the user name and password form (`/Users/AuthenticateByName`) in place of the code (D143 1); a server that does not answer, or answers with a network, timeout, http or parse error, shows "Couldn't reach Jellyfin at <address>." and lets the household change the address, on the card and in the sheet. The card's choice of server carries a visible label, "Your media server", and the card and the sheet give the same instruction ("In Jellyfin, open your user menu, choose Quick Connect and enter this code"). A revoked token (401) is an `auth` error with "Sign in again". Only the access token is stored (in `plexToken`, which is in `SECRET_KEYS` and never exported without the secrets option); the password is never stored. `DeviceId` in the `Authorization: MediaBrowser Client, Device, DeviceId, Version, Token` header is the display's own client id, which is no setting and is never exported.
- **Ratings (fail closed, D5, D134 3, D141 1, 5, D147 1).** An item's rating is its `CustomRating` when that is not empty, else its `OfficialRating`. A `CustomRating` or `OfficialRating` that is present but not a string makes the rating unknown, never a fallback to the other field. A reply with no `Items` array (or entries that are not objects) is a `parse` error, never an empty list. It counts only when it is exactly a US film or TV value on the ladder (`G`, `PG`, `PG-13`, `R`, `NC-17`, `TV-Y`, `TV-G`, `TV-Y7`, `TV-PG`, `TV-14`, `TV-MA`); `15`, `12A`, `NR`, `PG13`, `US-PG`, a lower-case value, a country-prefixed value and an empty one are unknown and hidden under any limit. Jellyfin's own parental controls are not relied on, and the `OfficialRatings` request filter is an optimisation: the engine checks every poster.
- **Posters.** Only `Movie` items with a primary image become posters (from a library, a BoxSet or a playlist; a BoxSet or playlist replaces the libraries). The year, runtime (`RunTimeTicks`), summary, genres, play count (`UserData.PlayCount`, a missing one is 0; an item counts as watched by one rule in a collection, a playlist and the library pool: `UserData.Played`, else `UserData.PlayCount` above 0) and audience score (`CommunityRating`) map to the fields the engine reads; a missing runtime, score or year is left empty. The image URL carries the token as `api_key`; the offline cache stores no token. Ids are Jellyfin's own, as written.
- **Now playing.** As for Plex: the session picked is the first playing one after the user filter; an item that is neither a movie nor (when included) an episode shows nothing. An episode shows its series poster; the live check uses the episode's own rating (D75) and the series' rating, read from the series, goes to the offline cache only (D73); a series whose rating cannot be read leaves the episode as unrated for the cache. The playing items are read again as items, because a session's own item may lack the `CustomRating`; when that request fails nothing is shown on an unchecked rating, and a playing item the reply leaves out is unrated (hidden under any limit), never judged on the session's own rating.

**R-SRC-3 (D134, D144, D145) Emby as a source.** A household with an Emby server picks Emby as the server type, signs in with a user name and password, and gets what a Jellyfin household gets, failing closed on any rating it cannot read and on any reply the adapter does not recognise. The adapter is `js/sources/emby.js`; it shares the items, the poster mapping and the rating map with the Jellyfin adapter (`js/sources/jellyfin.js`), so every Jellyfin rule above (R-SRC-2: ratings, posters, collections and playlists, now playing, the switch, offline) applies to Emby unchanged (D145). It is tested against the mock server in its Emby mode (`scripts/mock-jellyfin.mjs`: a request that carries `X-Emby-Authorization` is an Emby request), and every Emby path or field is a (verify) row in `docs/validation/real-server-extended.md` section J.
- **Signing in.** The server address comes first. The sign-in is `POST /Users/AuthenticateByName` with `Username` and `Pw`, and the header `X-Emby-Authorization: Emby UserId="", Client="Now Showing", Device="Now Showing", DeviceId="<the display's id>", Version="<app version>"` (no token before sign-in). Every later request carries the same header and the access token as `X-Emby-Token`; the poster image URL carries the token as `api_key`, and the offline cache stores none. Emby has no Quick Connect: the first-run card and the Settings sheet show no code and no Quick Connect button, only the user name and password form (on the card it takes the place of the code and hands the token to Settings). A server that does not answer, or one that refuses a cross-origin request, shows "Couldn't reach Emby at <address>. Check the address and try again." on the card (with the address field shown, filled and focused) and in the sheet (the address field focused), so the household can change it (D143 1, D145 8); no proxy is added. The libraries are listed at `GET /Users/{UserId}/Views` (Emby has no `/UserViews`; the paths are sourced in `js/sources/emby.js` and section J), with the user id the sign-in returns; a display holding an Emby token but no user id is told to sign in again.
- **What is stored.** The password is never stored, drafted or logged; the access token is the only secret, in the one token key (`plexToken`, in `SECRET_KEYS`). The user id the Emby sign-in returns is stored in `serverUserId` (not a secret, D145 2); it goes with its token: an import that sets the token aside sets it aside too. A failed sign-in stores nothing, and a sign-in stores nothing until Save. A user name is stored only in the existing "Only for this user" field.
- **`/Sessions`.** A `/Sessions` reply that is a 401, 403, 404 or any other HTTP error, or does not parse, means nothing is playing and never shows an error card or a toast (a user who may not list sessions gets 401 or 403). A network error or a timeout is still the server not answering. The item re-read of a playing item is not covered by this rule: when it fails nothing is shown on an unchecked rating. A reply the adapter does not recognise on any other route (not JSON, no `Items` array, a field of the wrong type) is a `parse` error; a null or missing rating is unknown, and so is one that is not a string, and each is hidden under any limit (D145 3, D147 1; the same rule holds for Jellyfin).
- **A token never goes to another server (D144 1).** For every server type, an import that changes the server address, or the server type, and brings no token of its own sets this display's token aside: the form has no token, the sheet asks to sign in, and nothing carrying the old token is sent to the new address. A file that brings a token keeps it; a file for the same address changes nothing.
- **The sheet after an import (D144 2).** An import made while the sheet's opening connection test runs ends that test: the line under the Test button reads "Connection not tested yet. Press Test connection." (or the test's own result), never "Connecting…".
- **Another server (D147 2, 3, 4; refined by R-SRC-4, D156 3).** A Save that stores another server address, within one type or across types, clears the pinned poster (a type switch clears the cache and the history as well; another address of the same type leaves them, and cached posters still pass the limit in force). Once the server's own id is recorded (R-SRC-4), the id decides instead: another address whose server has the same id keeps the pin, the cache, the history and the token, and a different id, or none readable, clears all three and sets the token aside. With several servers a switch or a different id clears that server's entries only. After an import that sets the token aside the sheet's connection line reads "Connection not tested yet. Press Test connection.", never the old server's "✓ … libraries". On a phone at rotation 90 the first-run card scrolls inside itself, so "Sign in" and "Open settings" stay reachable; in Settings Emby's user name and password form is shown open with a primary Sign in button, and an Emby sign-in shows no code placeholder and no Quick Connect line.
- **The switch toast (D144 3).** A Save that changes the server type and leaves no token says "The server type is now <server>. Sign in to <server> to show its posters. The offline posters, the pinned poster and the no-repeat history were cleared." The sentence of R-SRC-2 ("Now showing posters from <server>…") is kept for a switch that leaves a token.

**R-SRC-4 (D156, D157, D160) Several servers.** A household with more than one media server, up to three and any mix of Plex, Jellyfin and Emby, chooses libraries, genres, ratings, a collection or a playlist across them and gets one pool sampled fairly across them. The household limit is one ceiling over every server: every poster passes `allows()` with the limit in force, whichever server it came from, and no server's own parental control stands in for it. A household with one server sees no change (the plain adapter is used and no stored key differs from 2.4.0). Everything below is tested against the Plex mock and the Jellyfin mock, which serves Jellyfin and Emby (`scripts/mock-plex.mjs`, `scripts/mock-jellyfin.mjs`); every shape they invent is a (verify) row in `docs/validation/real-server-extended.md` section K. The server carried over from 2.4.0 is always the first server, and reordering the servers is not offered (D167).

- **The list.** The settings keep the first server in the keys 2.4.0 had (`serverType`, `serverUrl`, `plexToken`, `serverUserId`, `serverName`) and up to two more in `servers`, each `{ id, type, url, token, userId, name }`. A settings object from 2.4.0 loads as a list of one and nothing is rewritten. A fourth stored entry is dropped on load, and Settings refuses a fourth server. An entry needs its server id, type and address; an entry whose id is already in the list is dropped (the later one), and adding a server whose id is in the list is refused with "<name> is already in the list."
- **A server is known by its own id (D156 3).** Plex's `machineIdentifier`, or the `Id` of Jellyfin's or Emby's `/System/Info/Public`; the adapters read it without a token (`publicIdentity()`: Plex `GET /identity`, Jellyfin and Emby the public info). The first server's id is stored in `serverId`, when it is first read: at the first address change or when a second server is added.
- **Ids by server (D156 2, D157 1, 12).** Every id a server gives (a poster's `ratingKey` and `thumb`, a library, a collection or a playlist) is either bare, as 2.4.0 stored it, or scoped, `@<server id>/<id>`. No server id contains "/" and no server gives an id that starts with "@", so a bare id never reads as scoped. A bare id belongs to the one entry that owns the bare ids (`serverCarried`, true when absent), never to a list position, and to no other (D162 1). That is the entry carried over from 2.4.0, or a server that replaced it in the first place while alone, after the bare entries were cleared. The carried entry's own ids stay bare, and every other server's are scoped by its id; a server moved into the first place from the list (the first server was removed) keeps its scoped ids and is never carried. A display whose settings hold any scoped id uses the multi-server source, whatever the count. The carried entry is always the first one, and the list cannot be reordered. The offline cache, the pin, the no-repeat history, the library keys and a collection or playlist all use these ids. The same film on two servers is two items, and no-repeat applies per item (D157 13).
- **The pool.** One source (`createSources`) stands over the servers with the adapter interface. Each chosen library is asked for in proportion to the title count its server reports, before the rating filter, as for one server (D157 10); a collection or playlist is one source on one server and replaces every chosen library (D107 1). A genre is matched by its title on each server. A server that does not answer contributes nothing and the others carry the pool; the call fails only when every server fails (D157 5). The session that counts is the user filter, then the first one playing, over all servers in list order (D157 8).
- **Tokens (D157 3, 4).** Each entry has its own token, in `SECRET_KEYS` (`plexToken`, `servers.token`), never exported without the secrets option, and goes only to its own entry's address. At a changed address the server id is read without a token first. The token stays only when the id is the recorded one; otherwise it is set aside and the household signs in. An entry whose id was never recorded (a 2.4.0 object) is compared with the id read at its old address.
- **Changing and removing a server (D156 3, D157 2, 9).** Removing a server, or a change of address or type that reveals a different id (or none on Save), clears that server's cached posters, its pin, its no-repeat history and its libraries in the selection and the profiles, and nothing of the others. A new address with the same id keeps them, the pin included; for an entry with no recorded id (2.4.0) the pin still goes and the cache and history stay, as in 2.4.0 (D147 2, D143 6). A change of type is always another server. A server that is only down keeps its entries and contributes nothing; an offline draw takes the entries of every server in the list and none of one that is gone. Removing the carried entry clears the bare keys, and no other server inherits them: the removed server's libraries, collection and pin go from the selection and from every profile (D162 2), and the server moved into the first place keeps its own scoped ids, its pin and its token at its own checked address. If its address or type is then changed, its token is set aside until the id read there without a token matches its own (D157 3), it is still never carried, and the removed first server and its bare keys go (D162 1, 2, 3). A Save that changes nothing about any server asks no server anything, and a chosen library, collection or pin of a server that did not answer the test is kept; only a removed server's keys leave. Every non-connection setting, the limit first, takes effect at Save before any server is read (D162 5). The Save toast says what was cleared and which servers' posters show now, or names an added server and says to choose its libraries when none is chosen (D162 4).
- **The pin.** A pin names one server. A server that is gone, or an id it no longer holds (an HTTP 404), unpins it and says so; the id is never looked up on another server (D122 1). A server that is only down keeps the pin.
- **Settings.** The server list (inside the connection section) shows from two servers, with a Remove button on each, and an Add a server form (Plex: a plex.tv code; Jellyfin and Emby: address, user name, password) is always there while there are fewer than three. The section heading reads "Media server connections" when there are several servers. The "Connected to" card and the status pill and empty card name every server ("Can't reach Plex and Jellyfin"). Libraries, genres, collections and playlists are offered across the servers, each server's libraries under its name. Test connection says per server which answered, with its library count, and which did not, and offers the libraries of every server that answered. Nothing is stored until Save, and Cancel undoes an add or a remove.

## Settings model changes

All new keys are added to `SCHEMA` in `js/settings.js` in one phase (`settings-and-schedule-core`) with sanitisers that coerce bad input to the default, so later phases consume them and do not edit the schema. New helper sanitiser `hhmm` (`HH:MM`, 00:00-23:59, else default). Existing keys are unchanged. `EXPORT_VERSION` stays 1 (purely additive: older exports import with defaults; a new export imported by an older app has its unknown keys dropped by `sanitize`). `settingsPinHash` and `settingsPinSalt` are never exported and never accepted from an import file (new `NEVER_EXPORT_KEYS`). `config.json` provisioning accepts all settings keys except those two, plus the control flag `resetPin` (not a setting).

| Key | Default | Rule | Protects / why | Req |

## Security and privacy

- **Token handling**: stored in `localStorage` on the device. Never in a QR code, helper response, receipt, Diagnostics (already truncated to 4 characters), log line, or export unless ticked. It does appear in Plex request URLs by design (principle 4); a Jellyfin or Emby token travels in a request header and also as `api_key` in that server's poster image URLs (an `<img>` cannot send a header).
- **Git history** holds an old token (S1): rotate it (required); purge optional and skipped unless the repository is public or shared (D14).
- **`config.json`** is a token file: loopback-only with a hostname-only Host check (R-SEC-1), git-ignored, and the README says to delete it after first run. The server serves an allowlist of app paths only (D9).
- **Local helper** is the only listening surface the plan adds: opt-in `--helper`, loopback-only, shares `isLoopback`/`isLoopbackHost`, custom header, never a shell, validated inputs, no CORS grant (D8).
- **PIN** is client-side deterrence, not authentication; the UI says so (D16). Recovery is a loopback `config.json` flag (D10).
- **Least privilege Plex access**: managed user restricted to one library (R-DOC-6); IoT VLAN (R-DOC-5).
- **Privacy**: "Playing in {room}" and user names are shown on the display only; the Plex token goes to the user's own Plex server and to plex.tv; a Jellyfin or Emby token goes to that server only, and with several servers each server's token goes to that server's own address only (R-SRC-4), also as `api_key` in its poster image URLs. The token is set aside, and so not sent to the new address, in three cases: a change of server type (D142 2), an import that changes the server and brings no token (D144 1, D149 2), and a changed address whose server id, read there without a token, is not the recorded one or cannot be read (D157 3; for a server whose id was never recorded, the id read at its old address stands in). A server address typed in Settings receives the token only after the server there has been read without a token and found to be the same server (R-SRC-4): the connection test and Save send it there then, and not before. A server moved into the first place when the first one is removed keeps its own token (D162 3). Nothing else is sent anywhere.
